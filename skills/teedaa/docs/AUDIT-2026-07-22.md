# teedaa — read-only audit report

**Provenance:** `~/.claude/skills/teedaa` · branch overnight-loop/2026-07-22 · commit e6de456 · clean tree · 2026-07-22 · scope FULL · stack: Python 3.9 stdlib CLI + self-contained HTML dashboard

## Executive summary

teedaa is structurally sound and its rule-zero design holds on the paths it actually generates — but the untrusted-input hardening the design promises has real gaps. The adversarial gate confirmed **8 High** issues (none refuted): two are stored-XSS holes in the dashboard where a hostile *filename* in a scanned tree becomes live JavaScript when the report is opened; three are containment/kill-switch gaps where a tampered plan file or a symlinked path could let `apply`/`undo` rename outside the audited root, or let `report`/`plan` touch a cloud placeholder with the no-download guard unarmed; one is a data-durability gap where a hard crash mid-`apply` can leave moved files that `verify` then falsely vouches as all-clear; one wipes the freshly-built index on `--rescan`. Counts: **Critical 0 · High 8 · Medium 6 · Low 12 · Suggestion 9**. No baseline present — every finding is NEW.

**Top fixes:** (1) escape every `<` in the dashboard's embedded JSON so no filename can break out of the script tag; (2) esc() the one file-extension string that reaches innerHTML raw; (3) resolve symlinks before `apply`/`undo` trust a path is inside the folder; (4) arm the no-download kill switch in `report`/`plan`/`verify`/`undo`, not just `scan`/`apply`; (5) write each `apply` manifest row to disk *before* the rename, and re-seed the schema row after `--rescan`.

**`FS-bf4c8253` — apply escapes realpath(root): load_plan containment uses normpath, which does not resolve symlinks**  
*High · Likely · fix-risk Needs-verification · scripts/executor.py:135*

- **What:** load_plan() is the sole gate that keeps `apply` from moving anything outside the scanned root. It compares os.path.realpath(root) against os.path.normpath(op["src"]) / op["dst"]. normpath is purely lexical: it collapses '..' (so '..'-based escapes are correctly refused) but it does NOT resolve symlinks. So an operation whose path traverses a symlink that lives inside the tree passes the containment check, while the subsequent os.rename() in apply_plan (line 186) follows that symlink and operates on a file OUTSIDE realpath(root). Both directions escape: a symlinked src pulls an external file into quarantine (removing it from its real home), and a symlinked dst-parent writes the moved file into the symlink's external target.
- **Why it matters:** This directly breaks rule zero's core promise that apply may ONLY os.rename inside the root. The ops_sha256 stamp is a plain, keyless sha256 (planner.ops_checksum) that anyone can recompute, and the plan JSON is explicitly an untrusted, user-editable input; the path-containment check is the real security boundary and it is defeatable. Preconditions: (1) a crafted/edited plan file with a matching recomputed ops_sha256, and (2) a symlink present inside the tree (e.g. `evil -> /`), which an attacker who can write into a shared Dropbox tree can plant. With both, `apply` os.renames /etc/passwd (via root/evil/etc/passwd, whose lstat and size the attacker sets to match) into the quarantine, or writes into an external directory via a symlinked dst parent. The scanner itself never descends symlinked dirs (entry.stat follow_symlinks=False treats them as non-dir entries), so a *legitimately generated* plan is safe — the exposure is exactly the untrusted-plan case the guard exists to defend.
- **Fix:** Resolve symlinks before the containment test. For each op path, verify os.path.realpath(os.path.dirname(path)) is equal to rr or startswith(rr + os.sep) (the parent must be the real, resolved directory; the final component is what rename acts on and must not be resolved). Additionally reject any op whose path contains a component that is a symlink escaping the root. Do not simply realpath the whole path, since that would wrongly resolve a symlink you intend to move as its final component.

**`DAT-e8dd8afd` — apply renames files BEFORE their manifest row is durable — a hard crash leaves moved files with no manifest record, and verify/undo then vouch a false all-clear**  
*High · Confirmed · fix-risk Safe · scripts/executor.py:198*

- **What:** apply_plan performs os.rename (line 186) first and only then appends the manifest row via buffered mf.write/cf.write; flush+fsync happens only every 200th op (i % 200 == 199) and at the end. On SIGKILL / python fatal crash, rows still in the ~8KB userspace stdio buffer (roughly 30-50 rows) are lost outright even though their renames already happened; on power loss, everything since the last fsync — up to 200 already-executed moves — can vanish from BOTH the in-tree manifest and the ~/.cache mirror. There is no crash window where the manifest over-claims, only where it under-claims.
- **Why it matters:** The unmanifested files were really moved: junk-plan files sit in _Quarantine/<plan_id>/<relpath> (findable by hand), but photo/screenshot plans relocate into shared Photos/YYYY/MM / Screenshots/YYYY trees where an unrecorded move is indistinguishable from pre-existing content. Worse, the safety tooling actively lies afterwards: verify_plans only checks rows that ARE in the manifest, so it reports OK, and undo reports 'undo complete ... 0 could not be restored' while leaving the unmanifested files stranded in quarantine. README/skill flow then tells the user they may delete the quarantine folder after review — that deletion is the data-loss step, rubber-stamped by a false-green verify. This matters here because these runs happen unattended overnight (a mid-run death has already occurred once in this toolchain's history).
- **Fix:** Two safe, small changes: (1) write+flush the manifest row BEFORE os.rename — semantics stay correct because a row whose rename never happened lands in the benign 'already_undone'/'already_home' branch of verify/undo (dst missing, src present); (2) mf.flush()/cf.flush() after every row (cheap; eliminates the SIGKILL buffer loss entirely), keeping fsync at the 200-op cadence for power-loss bounding.

**`SEC-9f42da4f` — Stored XSS in generated dashboard: hostile filename with case-variant </SCRIPT> breaks out of the JSON script block**  
*High · Confirmed · fix-risk Safe · scripts/teedaa.py:1154*

- **What:** cmd_report embeds the aggregate payload (which contains attacker-controlled filenames and paths in tree node names, top100, junk samples, reclaim/protected paths, etc.) into a `<script id="D" type="application/json">` block via string substitution. The only breakout defense is `.replace("</script", "<\\/script")`, which is a case-SENSITIVE, lowercase-only match. json.dumps does not escape '<', '>', or '/', so a filename containing an uppercase or mixed-case closing tag such as `</SCRIPT>` passes through untouched. HTML end-tag matching inside script data is case-INSENSITIVE, so the browser closes the JSON script element early at `</SCRIPT>` and parses everything after it as live HTML.
- **Why it matters:** A file named e.g. `</SCRIPT><img src=x onerror=alert(document.domain)>.jpg` in the scanned tree lands verbatim in the JSON string. When the user opens dashboard.html, the HTML parser (not the JS `esc()` layer, which never runs on this data) terminates the script at `</SCRIPT>` and executes the injected `<img onerror>` — arbitrary JavaScript in the report's origin. Filenames are the explicit hostile-input trust boundary, and teedaa is designed to audit shared Dropbox trees where another person can create files, so the attacker-controls-a-filename precondition is realistic. The U+2028/U+2029 and lowercase-</script cases were deliberately handled here; the case-variant gap defeats the intended protection.
- **Fix:** Make the replacement case-insensitive and also neutralize `<!--`. Simplest robust fix: `payload = json.dumps(agg); payload = re.sub(r"</(script)", r"<\\/\1", payload, flags=re.I)` and also replace `<!--` with `<\\u0021--`, before the U+2028/U+2029 replacements. Escaping every `<` to `<` in the JSON is even safer and stays valid JSON.
- **Evidence:**

**`FS-e76b4023` — U+2028/U+2029 replacements are dead code (json.dumps already escaped them)**  
*Suggestion · Confirmed · fix-risk Safe · scripts/teedaa.py:1155*

- **What:** `json.dumps(agg)` runs with the default `ensure_ascii=True`, so every non-ASCII character — including the line/paragraph separators U+2028 and U+2029 — is already emitted as the 6-char ASCII sequence ` `/` ` in the payload. The subsequent `.replace(" ", ...)` / `.replace(" ", ...)` search for the literal raw separator characters (confirmed via hexdump: bytes e2 80 a8 and e2 80 a9 in the source), which can never appear in ensure_ascii output. The replacements therefore match nothing.
- **Why it matters:** Not a vulnerability — the raw separators cannot reach the payload, so nothing is corrupted and nothing is left unescaped by this omission. It is dead code that gives a false sense that separator-handling is active. It becomes load-bearing (and would then be correct) only if someone later switches to `ensure_ascii=False`; today it is a no-op.
- **Fix:** Either drop the two `.replace` calls, or (preferred, and this fixes findings #1 and #3 too) replace the whole chain with a single `.replace("<", "\\u003c")` on the json.dumps output, which is unconditionally safe for HTML `<script>` embedding. If ensure_ascii is ever set False, add `.replace(" ","\\u2028").replace(" ","\\u2029")` back with the raw chars.
