## The one rule

**Bump every version-bearing file in the same commit, to the same number.** A version that
disagrees between the git tag, the built app, and the artifact filename is the #1 cause of
a broken self-updater — the updater compares `releases/latest` tag vs the running app's
version, and matches the download asset by filename. One stale file and either the update
never offers, or it offers forever (a v0.2.0 build that shipped once will refuse every
v0.1.x update — a failure mode seen in VibeLight's history).

Don't hand-pick files from memory; **find them mechanically** (next section), bump each,
then run any post-bump hook. And before touching anything: **check the two zero-file
sections first** (Go, dynamic versioning) — in those ecosystems there is nothing to edit
and editing something anyway breaks the build.

## How to find every version-bearing file

Grep the repo for the **old** version string, with boundaries — a naked `0\.1\.5` also
matches `10.1.5`, `0.1.50`, and `0.1.5.2`:

```bash
git grep -nE '(^|[^0-9.])0\.1\.5([^0-9]|$)'   # the CURRENT version you're bumping FROM
```

Every real hit is a candidate. Skip hits that are:
- changelog / RELEASE_NOTES entries — those are history, leave them;
- a pinned *dependency* version that coincidentally matches;
- a comment;
- **lockfiles** (`package-lock.json`, `Cargo.lock`, `poetry.lock`, …) — regenerated by
  the ecosystem's own command, **never reviewed or edited by hand**. Exclude them from
  the eyeball pass entirely; the per-ecosystem sections say which need a resync command
  and which need nothing.
- a deliberately **independent version trail** (a helper CLI inside the repo with its own
  `VERSION` constant) — confirm intent before lockstepping it to the app version.

Bump the rest. Then re-grep for the **new** string to confirm every file moved together
(the [ship-time sanity check](#ship-time-sanity-check)).

## Go — the tag IS the version (no file to bump)

Go modules have **no version file. The annotated tag is the version.** Do **not** invent
one — no `VERSION` file, no constant, no `[project]`-style table. The module proxy and
`go install pkg@vX.Y.Z` read tags only.

- Tag format is strict: `vX.Y.Z`, full three-part semver, lowercase `v`, no omitted
  segments. `1.2.3` or `v1.2` are invisible to the module system.
- **Major versions ≥2 change the module path**: `go.mod` must read
  `module github.com/<owner>/<repo>/v2` and every internal import must gain the `/v2`
  suffix. A major bump in Go is a **code change plus a tag**, never just a tag.
- Binaries built from a tagged module get their version for free via
  `runtime/debug.ReadBuildInfo`. If a build script injects it instead
  (`-ldflags "-X main.version=..."`) — including via goreleaser — that's build-time
  stamping **from the tag**; leave the source alone.

For Go, "bump the version" in the ship sequence collapses to: pick the number, write the
notes, tag. Everything else in this file is a no-op.

## Dynamic versioning — detect and skip file edits

Some projects derive their version from git metadata at build time. For these, **the
annotated tag is the bump — skip file edits entirely.** Detect before you grep:

```bash
git grep -ln 'setuptools_scm\|setuptools-scm\|hatch-vcs\|use_scm_version' -- \
  pyproject.toml setup.py setup.cfg 2>/dev/null        # Python: setuptools-scm / hatch-vcs
ls GitVersion.yml .goreleaser.yml .goreleaser.yaml 2>/dev/null   # .NET GitVersion / goreleaser
git grep -n 'git describe' -- '*.cmake' CMakeLists.txt 2>/dev/null  # git-describe CMake
```

Also suspicious: a manifest with **no static version at all** (pyproject with
`dynamic = ["version"]`, a csproj with no `<Version>` but a GitVersion.yml beside it).

**Never edit a fallback or generated version file** (`fallback_version`, a cached
`_version.py`, a configure-generated header). It's ignored on correct builds — but a
tarball build or wrong-checkout build silently reports your edited fallback, and generated
files get overwritten or conflict on the next build. Editing them breaks builds; it never
helps them.

Two operational notes:
- setuptools-scm computes dev versions from **distance since the last tag** — a stale
  local tag list yields wrong versions. Step 0's `git fetch --tags --prune origin`
  covers this; don't skip it in these repos.
- The tag must be **annotated** (`git tag -a`) — the ship sequence already does this;
  some tools ignore lightweight tags.

## npm / pnpm / yarn (package.json)

`package.json` `"version"` is the source of truth. Edit it, then handle the lockfile
**by which lockfile exists** — this is where the wrong reflex mints garbage:

| Lockfile present | After editing package.json |
|---|---|
| `package-lock.json` | `npm install --package-lock-only` — syncs the lockfile's own-package entries without reinstalling or bumping transitive deps. Commit both files. |
| `pnpm-lock.yaml` | **Nothing.** pnpm's lockfile doesn't record the package's own version. Commit package.json only. |
| `yarn.lock` | **Nothing.** Same — yarn.lock has no own-version entry. Commit package.json only. |

**NEVER run `npm install --package-lock-only` in a pnpm or yarn repo** — it mints a
spurious `package-lock.json` beside the real lockfile, and now the repo has two package
managers fighting.

electron-builder derives the artifact name (`${version}` in `artifactName`) from
`package.json`, so this one file drives the dmg/exe name too — no separate bump.

**Subdirectory manifests** — the version doesn't have to live at the repo root:

- **cockpit-anchor**: the version is in `ui/package.json`; the repo root has no
  package.json at all. Bump the subdirectory file.
- **MusicSorter**: `app/package.json` (a pnpm repo — no lock resync). Plus its
  **tag-glob wrinkle**: the Electron release workflow triggers only on `v0.2.*`,
  `v0.[3-9].*`, `v[1-9].*.*` — `v0.1.x` tags belong to a legacy lineage and
  **deliberately build nothing**. A typo'd v0.1.x tag fails silently: no run, no error.
  General rule: before tagging, confirm the workflow's tag globs actually match the
  number you picked (`grep -A3 'tags:' .github/workflows/*.yml`).

Root-package.json worked examples: FLACtoiPod, Folderify, robogearsDownloader,
3rdPlayerScreen4Rekordbox (all Electron, all npm).

## Python (pyproject, poetry, version constants)

Three layouts — figure out which one you're in before editing:

1. **PEP 621 `pyproject.toml`** (hatch, uv, setuptools, flit): bump
   `version = "X.Y.Z"` under the `[project]` table. No lockfile resync needed for a
   version bump (uv.lock/pip don't gate on the own version the way Cargo does).
   **Trap:** a `pyproject.toml` that is **only tool config** — `[tool.pytest.ini_options]`,
   `[tool.ruff]`, no `[project]` table — is **NOT the version source** and the repo is
   not a packaged project. Don't add a `[project]` table mid-ship; look for a version
   constant instead (layout 3).
2. **Poetry**: `poetry version X.Y.Z` bumps `[tool.poetry].version` (or `[project]` on
   Poetry ≥2). `poetry.lock` doesn't record the own version — no resync.
3. **Plain `__version__` / constants** — unpackaged apps and servers carry the version
   as a hand-maintained constant: `__version__ = "X.Y.Z"` in a package `__init__.py`,
   or an `APP_VERSION` in a constants module. The discovery grep finds these; bump them
   like any other file.

**The dual-constant hazard (layout 3's failure mode):** a repo can grow **two**
hand-maintained constants that drift — typically one the app's version endpoint actually
serves and one a release commit bumped. Worked example: odysseus carries `APP_VERSION` in
**both** `core/constants.py` and `src/constants.py`, and the two have drifted before (a
"v1.0" bump touched one file; the endpoint kept reporting the old number from the other).
Already drifted? `git log -S APP_VERSION --oneline -- <each file>` (or blame) finds the
most recent **deliberate** bump — that is the intended version; the endpoint-served copy
is what running installs *report*, decisive once an installed base/updater exists but not
before (the same which-number-wins rule as `project-type-detection.md`'s trap 5) — and
the release commit brings every copy to that one number.
When the discovery grep surfaces more than one constant: **consolidate to a single source
(import one from the other) or bump every copy in lockstep, same commit, every time.**
This is exactly why you grep for the old version instead of editing the file you remember.

If detection found setuptools-scm / hatch-vcs instead, none of this applies — see
[dynamic versioning](#dynamic-versioning--detect-and-skip-file-edits).

## Rust (Cargo.toml + Cargo.lock resync)

Bump `version = "X.Y.Z"` under `[package]` in `Cargo.toml`. Then the **mandatory
lockfile resync** — `Cargo.lock` records the own package's version, and a stale entry
fails every `cargo build --locked` / `--frozen` CI build:

```bash
cargo check    # regenerates Cargo.lock's own-package entry; touches NO dependency versions
```

Plain `cargo check` is sufficient — no `cargo update -w` needed (that flag exists but buys
nothing here). **Commit both `Cargo.toml` and `Cargo.lock`.**

Workspaces: members with `version.workspace = true` inherit from
`[workspace.package].version` at the root — bump that one place, then the same
`cargo check`, then commit the root manifest + lockfile.

## C# / .NET (csproj `<Version>`)

The version lives in the `.csproj` as `<Version>X.Y.Z</Version>`. Bump that element:

```xml
<PropertyGroup>
  <Version>0.1.14</Version>
</PropertyGroup>
```

**The CI `-p:Version=$tag` wrinkle** (worked example: VirtualMirage,
`src/VirtualMirage/VirtualMirage.csproj`): a release workflow may *also* inject the
version from the tag via `-p:Version=` on the `dotnet publish` line — so the shipped
binary's version comes from the **tag**, not the csproj. **Keep the csproj `<Version>`
and the tag identical anyway**: local builds and the assembly identity read the csproj,
and the in-app updater compares the assembly version — let them drift and dev builds
disagree with shipped builds about what version they are. (An `app.manifest`
`assemblyIdentity version` is cosmetic and can stay `0.1.0.0`; the real version is
csproj + tag.)

If a `GitVersion.yml` sits beside the solution, the version is tag-derived — see
[dynamic versioning](#dynamic-versioning--detect-and-skip-file-edits) and don't touch
the csproj.

## Swift / macOS (XcodeGen project.yml or raw pbxproj)

**Variant A — XcodeGen** (a `project.yml` exists; the `.xcodeproj` is generated, never
hand-edited). Bump `MARKETING_VERSION` in `project.yml` — it may sit under the top-level
`settings.base` or under `targets.<name>.settings.base`:

```yaml
settings:
  base:
    MARKETING_VERSION: 0.1.7
```

Then regenerate so the build picks it up: `xcodegen generate`. Do **not** edit the
pbxproj directly — the next `xcodegen generate` overwrites it. Worked example: VibeLight —
its updater's asset contract is `*-arm64.zip`, and the version in that filename comes from
the build reading `MARKETING_VERSION`, so this is the load-bearing bump.

**Variant B — raw Xcode** (no project.yml; the pbxproj is source). `MARKETING_VERSION`
appears in **multiple build configurations** — at minimum Debug + Release per target, more
with extra configs or targets. Bump **all of them**:

```bash
grep -c 'MARKETING_VERSION' *.xcodeproj/project.pbxproj   # know how many you must change
agvtool new-marketing-version X.Y.Z                        # updates every config at once
```

`agvtool` (run from the project directory) is the safe path; hand-editing is fine only if
the re-grep afterward shows every occurrence moved. Then `Info.plist`:
`CFBundleShortVersionString` is usually `$(MARKETING_VERSION)` — nothing to do — but if a
target hard-codes a literal version string there, bump it too. Missing one config is the
classic "the Release build reports the old version" bug.

## CMake / C++ (project VERSION, CMake vars, version-in-code)

**Generic CMake:** the version lives in the `project()` call:

```cmake
project(MyApp VERSION 0.2.5)
```

That feeds `PROJECT_VERSION` / `MyApp_VERSION` and anything `configure_file`d from them.
Never edit a **generated** version header — it's build output; edit the `project()` line
(or the variable that feeds the template) and rebuild.

**Version in a CMake variable** (worked example: VibeEden,
`CMakeModules/GenerateSCMRev.cmake`): some projects keep the version in a bespoke
variable that a script `configure_file`s into a source file along with other build
metadata (VibeEden bakes the version *and* the updater endpoint into `scm_rev.cpp`):

```cmake
set(VIBEEDEN_VERSION "0.2.5")
```

Load-bearing gotcha documented in that file: `GenerateSCMRev.cmake` **unconditionally
overwrites** `BUILD_VERSION` with `VIBEEDEN_VERSION`, so the surrounding git-describe
logic is dead code — the variable is the single knob. Also check the repo's release
workflow before tagging: one that publishes with `make_latest: true` and no `draft: true`
(as VibeEden's has historically) goes **public the moment the tag builds** — there is no
draft to catch a bad bump, so triple-check the number first. (If the git-describe logic
is *live* — the variable is only a fallback — that's
[dynamic versioning](#dynamic-versioning--detect-and-skip-file-edits): tag, don't edit.)

**Version-in-code C++** (worked example: VibeDolphin,
`Source/Core/Common/Version.cpp`): the version can be a hand-maintained **brand string
in a `.cpp` that the in-app updater parses at runtime** — VibeDolphin's
`GetScmRevStr()` returns a string shaped `"VibeDolphin 0.1.17"`, and its updater takes
the last whitespace-delimited token as the current version. Bump the string in the
source file. **The string's shape is a contract with the updater's parser** — keep the
exact `Name X.Y.Z` format; a reworded string bricks version comparison for every user
on the next check.

Embedded/helper repos may have **no version bump at all**: a fork built purely to be
embedded in a host app (e.g. vibelight-moonlight-helper inside VibeLight) has no
independent release — leave its upstream version file alone; it ships by shipping the
host app.

## Gradle / Maven

- **Gradle:** `version = "X.Y.Z"` in `build.gradle` / `build.gradle.kts`, or
  `version=X.Y.Z` in `gradle.properties` — check both; when the build script reads the
  property, the properties file is the one to bump.
- **Maven:** `<version>` in `pom.xml`. In multi-module builds don't hand-edit every
  child: `mvn versions:set -DnewVersion=X.Y.Z` moves the parent and all module poms
  together.

## Browser extensions (manifest.json)

`manifest.json` `"version"` — but first decide which of two cases you're in:

- **Primary version file** (a standalone extension repo): `manifest.json` IS the version
  source — bump it directly. Store constraint: Chrome requires 1–4 dot-separated
  integers, no `v` prefix, no suffixes — `1.2.3-rc.1` is rejected at upload, so
  prerelease tags can't flow into the manifest.
- **Synced copy** (the extension rides inside an app repo, manifest generated from the
  app's version): **never hand-edit the manifest** — bump the app's version file and run
  the repo's sync hook so the copy follows. The worked example is robogearsDownloader's
  `npm run sync-ext` — see
  [post-bump hooks](#repo-specific-post-bump-hooks-run-these-or-ship-broken).

## Multi-file lockstep bumps

Some repos carry the version in **several** files that must all move together in one
commit. Folderify is the worked example — its release checklist mandates bumping, in
lockstep:

1. `package.json` `"version"`
2. `package-lock.json` (via `npm install --package-lock-only`)
3. any UI copies of the version string (an "about"/settings display constant, if the app
   hard-codes it rather than reading `app.getVersion()`)
4. the iOS `project.pbxproj` **MARKETING_VERSION — in two build configs** (Debug +
   Release), since Folderify ships an iOS target from the same repo (the raw-pbxproj
   multi-config rule from the Swift section, inside an npm repo)

Miss the pbxproj and the iOS build's version silently diverges from the desktop one.
Same family of hazard as Python's dual constants (odysseus) and synced extension
manifests (robogearsDownloader) — different ecosystems, one rule: **every copy moves in
the same commit or the copies lie.**

Also: if a repo's `CLAUDE.md` header carries a "Current version:" line, bump it too —
checklists historically forget it (the `doc-drift-audit` skill catches the drift after
the fact; bumping it here avoids it).

Rule of thumb: after editing, `git grep -nE '(^|[^0-9.])<new-version-escaped>([^0-9]|$)'`
and eyeball that every file you expected to change actually did.

## Repo-specific post-bump hooks (run these or ship broken)

Some repos have a **script that must run after the version bump** to propagate the number
into a file the manual edit doesn't touch. Easy to forget — they live in the repo's task
runner, not in the obvious version files.

**General rule:** after bumping, check **every task runner the repo has** for a
sync/version helper and run it before committing:

```bash
# npm/pnpm/yarn scripts:
node -e "console.log(Object.keys(require('./package.json').scripts||{}).join('\n'))" 2>/dev/null \
  | grep -iE 'sync|version|bump|ext'
# Make / just / nox targets:
grep -ihE '^[a-z0-9_-]*(sync|version|bump)[a-z0-9_-]*:' Makefile justfile Justfile 2>/dev/null
grep -inE 'def .*(sync|version|bump)' noxfile.py 2>/dev/null
# Rust xtask pattern:
cargo xtask --list 2>/dev/null | grep -iE 'sync|version|bump'
```

**Worked example — robogearsDownloader:** `npm run sync-ext`
(`scripts/sync-extension-version.js`) copies the bumped `package.json` version into
`chrome-extension/manifest.json`. The in-app extension handshake compares those two
versions, so a ship that bumps package.json and skips the hook recreates the exact
manifest-mismatch bug the hook was added to fix (v0.1.29/v0.1.30 were cut to fix it).
So, every ship there:

```bash
npm run sync-ext        # propagates the bump into chrome-extension/manifest.json
git add chrome-extension/manifest.json
```

and stage the synced file **into the same release commit** — a hook whose output lands in
a later commit is the same drift with extra steps.

## Ship-time sanity check

Before committing the bump (boundary-guarded, same pattern as discovery):

```bash
git grep -nE '(^|[^0-9.])<NEW>([^0-9]|$)'   # every file you meant to bump appears
git grep -nE '(^|[^0-9.])<OLD>([^0-9]|$)'   # only history (RELEASE_NOTES/changelog) still matches
```

(`<NEW>`/`<OLD>` with dots escaped, e.g. `0\.1\.6`.) Lockfiles showing the new number via
their resync command are expected; lockfiles still showing the old number in a repo whose
section above says "resync" means you skipped the resync.

The **tag/manifest/notes consistency assert** — tag string equals the bumped version,
`RELEASE_NOTES.md` heading matches — runs at tag time and lives in **SKILL.md step 3**;
this grep pair is the pre-commit half, that assert is the pre-push half. Run both.

Then continue with `RELEASE_NOTES.md` (step 2 of `ship`) and the tag.
